# Pre-registration: consensus surprises at tick resolution (written 2026-10-13, before any tick around an event was looked at)

the trader: "prossegue com a ideia de fundo" (follow the consensus surprise), after the minute-bar study (EVENTS_RESULT.md: 0 of 18, the best p 0.0078 came almost entirely from 2022 and reversed in 2025). The reaction to a release is largest in the first seconds, which minute bars cannot resolve, so this family uses the real MT5 broker ticks.

## Facts and limits written first
1. Real ticks exist only from 2025-10-01; with calendar events up to 2026-08-15 (the export's end) there are only a few dozen strong USD events. **The sealed HOLD of this family is 2026-08-16 onwards: no tick after that instant is loaded.**
2. The MT5 calendar's `actual` value reaches the terminal some time after the scheduled release (seconds to tens of seconds; the history does not record that lag). Entries sooner than that lag cannot be made by an EA. So the study reports a timeline of delays, and only the delays of 10 and 30 seconds carry pre-registered tests; the live lag is to be MEASURED (a read-only logger on the next releases) before anything below 30 s is believed.
3. Latency 300 ms added to every entry and exit as in PREREG_HF.md; spreads at releases widen a lot: real ticks, real bid and ask.

## Events and trades
Events as in PREREG_EVENTS.md (importance 3, actual and forecast present, `impact` known, >= 8 previous releases of the same event measured on the whole file, strong |S| >= 1 with the causal sigma) restricted to releases 2025-10-01..2026-08-15, all currencies mapped as before; the USD pool uses the 8-asset basket (EURUSD, GBPUSD, AUDUSD, NZDUSD, USDJPY, USDCAD, USDCHF, XAUUSD, at least 5 present). Entry at the ask (long) / bid (short) of the last quote at release + delay + 300 ms; exit at the bid (long) / ask (short) of the last quote at entry + hold + 300 ms; follow the surprise.
**Primary tests (4):** USD pool, delay in {10 s, 30 s} x hold in {60 s, 300 s}; Bonferroni 0.05/4 = 0.0125; statistic = mean net bp, null = block sign-flip of the surprise direction (blocks = release timestamps, 20,000 flips); a test passes if p < 0.0125 and the mean net is positive and at least 40 events are traded. The placebo calendar (release times +7 days, same weekday and clock time, surprises kept) runs through the identical code first and must pass 0 tests.
**Descriptive profile (no test):** the mean signed mid-price move (follow direction, bp) and the mean spread (bp) at -60 s, -10 s, -1 s, +1, +2, +5, +10, +30, +60, +300, +900 seconds around the release, over the strong USD events, plus the same table for tier-1 events: where the surprise is absorbed and what it costs to be there.
**Not done in this family:** limit orders (they do not earn the spread on MT5), non-USD events (too few), anything after 2026-08-15.

## Expectations written now
The information is fast: most of the signed move is expected within the first seconds, when the spread is several times its normal size and the calendar value may not be visible yet; what is left at 10-30 seconds is expected to be about the size of the cost. With a few dozen events only a large effect can pass. The most likely outcome is no passing test; the profile is the useful part, and it decides whether measuring the live calendar lag is worth doing.

## Amendment 1 (2026-10-13, before the first valid run): a clock error in my first run
The first execution (placebo and real) compared the calendar release instants (UTC) with the tick epoch treated as UTC. The MT5 Python API returns times on the SERVER clock (Europe/Athens, naive): proof, the daily spread peak (4.96 bp) sits at hour 0 of the tick epoch, exactly as in the M1 files already known to be on the server clock. The first run was therefore misaligned by 3 hours (2 in winter): it measured 3 hours before each release (no reaction, flat spreads, a net equal to the random-direction mean). It is INVALID and no conclusion was drawn from it. Fix: calendar UTC times are converted to the server clock before any tick lookup; the sealed HOLD boundary (2026-08-16) is the same instant on the server clock. Tests, thresholds, null and placebo are unchanged.
The same error exists in the HF family (hf_data.py treated the tick epoch as UTC when computing the server hour, the weekday and the event features): its rollover exclusion hit the wrong hours (the true rollover was left in), its event features were 3 hours off. Handled separately (rebuild and rerun, see CLAUDE.md).
