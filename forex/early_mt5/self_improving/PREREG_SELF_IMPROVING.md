# Pre-registration: the self-improving trader (written 2026-10-12, before any run)

the trader: "(original wording omitted)". Source: the six @fidetolabs reels (reels/NOTAS). Their lessons become the design rules: point-in-time data, one clock, a universe fixed before the join, an append-only claims file, and the score you trust is the one measured on what was known at the time.

## What is built (v1)
`forex/early_mt5/self_improving/` = platform_pit.py (point-in-time tables), grammar.py (strategy specs), loop.py (the agent), promote.py (gate against the installed system, written after the loop has run once).
- **Data platform.** Four index CFDs on MT5 broker data (SP, NSDQ, DOW, DAX), one decision bar per day (1 minute before the cash close: 15:59 New York, 17:29 Berlin). Every feature at day i uses only closes up to and including day i; entry is the ask of that same bar, exits are decided on a later day's bar and filled at its bid. Universe fixed before any join (the four markets); coverage printed.
- **Specs (the agent's strategy language).** Families: rsi_dip (RSI n in 2/3/4 below th, optional trend filter close>SMA100/200, optional vol regime), low_dip (close at k-day low), pop_short (RSI above th, below SMA200, short), breakout (k-day high). Exits: SMA5/SMA10/RSI cross/time stop, max hold. Spec space is a few thousand cells, enumerated by `grammar.py`.
- **The loop.** Generation 0 = random specs; later generations = 60% one-parameter mutants of the best specs of the previous generation, 40% fresh random. Every spec is hashed, run once, and appended to `SI_LEDGER.csv` (append-only: the agent may add rows, never edit them). Each generation appends a few lines to `SI_LESSONS.md` (which families survived, counts).
- **Honesty built into the loop.** (1) The significance bar uses the CUMULATIVE number of specs ever in the ledger: Benjamini-Hochberg q=0.10 over every DEV p-value ever recorded, so the agent pays for its own search. (2) Economic floor: mean >= 3 bp per trade after the real bid/ask. (3) Minimum 80 trades on 40 decision days. (4) DEV = 2022-24, VAL = 2025, HOLD = 2026-01..09 stays sealed in the loop (never read by it). (5) PLACEBO mode: the same loop on price paths rebuilt from 20-day-block permutations of the real returns (real spreads kept); the number of 'survivors' there is the loop's false-discovery rate and must be reported next to the real result.

## Acceptance bars (fixed now)
S1 DEV survivor: one-sided p passes BH at q=0.10 over the cumulative ledger, n >= 80 trades on >= 40 days, mean >= 3 bp.
S2 VAL pass (2025, one look, only for S1 survivors): mean > 0 bp, n >= 25, one-sided p < 0.20.
S3 HOLD (2026, one look, spent when read, only for S2 passes): mean > 0 bp, n >= 8.
S4 against the installed system (promote.py): the spec's trades go through the same day-array machinery (stop 3 sigma, day risk 500 x 0.75, guard 1,500) as an add-on leg to the installed system, fresh account, MIX pools. Replacement candidate only if P(pass within 44 business days) is >= installed + 3 points AND the breach by 60 days is <= installed + 1 point (the same bar as the IM1 round: PREREG_IMPROVE.md). Then, before anything touches the account: an MT5 real-tick tester run on MT5 broker data of an EA built from the spec (the Python screen overstates pattern strategies: S3 +0.13 R Python vs PF 1.13 tester; FVG +0.16 vs +0.06) and a forward period on the live log.
S5 calibration: if PLACEBO produces survivors at S1 at a rate comparable to the real run, the real survivors are not evidence.
Nothing here changes the live account. Replacement of any live leg is the trader's decision, executed by hand.

## Expectations written now
The families here are variations of dip-reversal/RSI(2) already tested in PREREG_RSI2_LEG.md (leg adds about +1.3 points at 44 days). The most likely outcome of v1 is: a few S1 survivors that are RSI(2)-like, none that clear S4. The value of v1 is the machine (cumulative honesty, placebo, ledger), not a new edge; a real chance of improvement would need new information (alternative data, other markets) fed through the same platform.

## Amendment 1 (2026-10-12, after the v1 run, before any v2 run): v1 failed calibration (S5)
v1 result (ledgers SI_V1_*): real run 2,400 specs -> 662 S1 survivors and 407 VAL passes; PLACEBO worlds (structureless prices, same drift and spreads) -> 90, 373 and 262 survivors. A loop that finds 'edges' in noise has no evidential value: the 662 real survivors are NOT evidence.
Cause found: the test asks 'mean > 0', and a long-biased spec on an index that drifts up (3-5 bp per day in 2022-25) passes it in any world; subtracting drift x holding days removed about a third of the survivors' mean (32.7 -> 22.5 bp), the rest is the winner's curse of the search.
v2 change (fixed now): the tested return is the EXCESS over holding the same index for the same days (a short is charged the drift); drift measured per market through 2025-12-31 only; all else unchanged (BH over the cumulative ledger, floors on the excess mean, same DEV/VAL/HOLD). v2 uses new ledgers (SI_LEDGER_V2.csv, placebo SI_PLACEBO_LEDGER_V2_*). Disclosure: the VAL year was looked at in v1 for the v1 survivors, so v2 VAL results are not a clean one-look; HOLD (2026) is still unread. v2 stands only if its placebo survivor count is about zero (S5), otherwise the loop gets a stricter null (random-entry permutation per spec) before it may claim anything.
